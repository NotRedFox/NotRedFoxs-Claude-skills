## Map
Built from the README Architecture section, the two branch maps and the code. Files read in full: README.md, app/auth.py, app/notes.py, app/search.py, app/server.py, tests/test_auth.py, tests/test_search.py, tests/test_server_audit.py, both earlier reports, and the diff of commit 7b8798c.

Branches: auth-api (app/auth.py, app/server.py) and notes-search (app/notes.py, app/search.py, the three note routes).

One process holds three module-level singletons in app/server.py: `AUTH = Auth()`, `NOTES = Notes()`, `SEARCH = Search(NOTES)`. `ThreadingHTTPServer` runs one thread per connection; no lock is held anywhere.

Where the branches connect:
1. `Handler._user()` turns the `Authorization` header into a username with `AUTH.user_for`. Every note and search route depends on it.
2. `POST /notes` calls `NOTES.create(user, body.get("text", ""))`, then (new in 7b8798c) walks `SEARCH.cache` and deletes the user's keys.
3. `GET /search` calls `SEARCH.find(user, q)`, which on a miss calls `NOTES.list_for(user)`, which walks every note of every user.
4. `GET /notes` calls `NOTES.list_for(user)`.
5. `SEARCH.find` assumes every note's `text` is a string; `POST /notes` stores whatever JSON value it was sent.

State: all in memory. `AUTH.users`, `AUTH.tokens` (never removed), `NOTES.notes`, `NOTES.next_id`, `SEARCH.cache`. Nothing persists across a restart.

What the fix commit changed: passwords are no longer lowercased; `Notes.create` uses `tags=None`; `POST /notes` clears the user's search cache; the 500 body is `"internal error"`.

## Findings

### F1. Clearing the search cache in POST /notes fails under concurrent searches. High
- Where: app/server.py, `do_POST`, lines 48 and 49: `for key in [k for k in SEARCH.cache if k[0] == user]: del SEARCH.cache[key]`. Added by commit 7b8798c.
- What happens: the list comprehension walks `SEARCH.cache` while other request threads add keys in `Search.find`. Python raises `RuntimeError: dictionary changed size during iteration`. The note is already stored by then, so the client gets 500 `{"error": "internal error"}` for a note that exists, and the user's cache is left uncleared, so their next search can be stale. A client that retries on 500 makes a duplicate note.
- How it was found:
  - Over HTTP, 20 searching clients and 4 note-creating clients for 30 s: `create_201: 2489, create_500: 7, create_None: 1`, all 500 bodies `internal error`. A second run with 8 readers: 1 POST 500 in 5,611.
  - In process, the exact server loop against 4 searching threads and 20,000 cache entries: 188 of 200 clears raised with the default switch interval, 200 of 200 with a 1 microsecond interval.
  - The cache gets that large from normal use: any user who searches without posting (A4 above).
  - Finding test `test_note_creation_does_not_fail_while_other_users_search` fails on every run (19, 22, then 16 of 30 creates got 201).
- Suggested fix: move invalidation into `Search` behind a `threading.Lock` that `find` also takes, or drop the cache (an uncached search over 10,000 notes took 0.41 ms in the notes-search audit). With the cache removed in /tmp/aud-final-fixed, the test passes.

### F2. Listing notes races with note creation and drops GET requests. Medium
- Where: app/notes.py `list_for` (`for n in self.notes.values()`), reached from `GET /notes` and from `GET /search` on a cache miss. app/server.py `do_GET` has no exception handler.
- What happens: while another user's `POST /notes` adds to `NOTES.notes`, the walk in `list_for` raises `RuntimeError: dictionary changed size during iteration`. In `do_GET` that closes the connection with no reply. It only shows when writers and readers from different users run at the same time.
- How it was found: 13,213 notes stored, then 4 writers and 8 readers for 30 s: 10,740 GETs answered, 1 `RemoteDisconnected`; the server log shows the traceback ending at `notes.py, line 20, in <listcomp>`. In the fixed copy (search cache removed), the searcher threads in the F1 test hit the same error 4 times. The long run errors (0 at 80 s, 29 at 300 s, rising as the note count rose) fit this, but their type was not recorded.
- Suggested fix: a lock in `Notes` around `create` and `list_for` (which also fixes A5), or iterate over `list(self.notes.values())`; add error handling to `do_GET`; keep notes per owner so a list does not walk everyone's notes.

### F3. Throughput falls as the total number of notes grows. Medium
- Where: app/notes.py `list_for` walks every note of every user; with the F1 fix each post clears that user's cache, so most searches are misses and each miss walks every note.
- What happens: long run, 8 users, each journey is login, create, two searches, and a list every tenth journey. 3,173 journeys in the first 20 s (159 per second), 1,066 in the last 20 s (53 per second) at 18,878 notes. One user's cost depends on how many notes all other users have.
- How it was found: long run samples below.
- Suggested fix: keep a dict of owner to note ids in `Notes`. This was Low (A10) in the notes-search audit; together with the cache clearing it now limits the whole system, so it is rated Medium here.

### F4. The stale-search fix sits in the HTTP route and has no test. Medium
- Where: app/server.py lines 48 and 49 change `SEARCH.cache` from outside `Search`.
- What happens: any caller of `Notes.create` other than the route still gets stale results (`test_search_sees_notes_added_after_an_earlier_search` still fails). Before this audit no test ran line 49 (coverage of the full suite: server.py 94 percent, missing 49, 71, 75, 76), and removing both lines left all 50 existing tests with the same results (mutation M1 below).
- How it was found: coverage and mutation M1.
- Suggested fix: give `Search` a method such as `forget(owner)` or make `Notes.create` bump a version that the cache key includes. `test_search_over_http_sees_a_note_added_after_an_earlier_search` now covers the route.

### F5. Stopping the server prints a traceback. Low
- Where: app/server.py `main`.
- What happens: SIGINT ends with `KeyboardInterrupt` and a traceback; `server_close` is never called. `python -m app.server notaport` ends with `ValueError: invalid literal for int()`. Restart on the same port right after works (got 401 from `GET /notes` within 1 s).
- Suggested fix: catch `KeyboardInterrupt`, call `server_close`, and validate the port argument.

### F6. Test servers use fixed ports. Low
- Where: tests/test_search_routes.py (8101), tests/test_server_audit.py (8102), tests/test_final_audit.py (8103).
- What happens: two suites at once, or anything else on those ports, make the tests error. Running the suite on one allowed port needed a rewritten copy.
- Suggested fix: bind port 0 in one shared fixture in `tests/conftest.py` and read the port from the server.

### F7. Fix commit names IDs that are in neither report. Low
- Where: commit 7b8798c, "Fix P1 P2 P5 P7 after branch audits".
- What happens: both reports number findings A1 to A12, and the two reports overlap. The commit fixes auth-api A1 and A4 and notes-search A2, A6 and part of A3, which cannot be read from the message.
- Suggested fix: reference report and finding, for example "auth-api A1".
