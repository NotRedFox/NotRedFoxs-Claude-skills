## Map
The README has an Architecture section; this map starts from it.

Entry points (app/server.py, `Handler`):
- `POST /register` {username, password} to `Auth.register`, 201 or 400.
- `POST /login` {username, password} to `Auth.login`, 200 {token} or 401.
- `POST /notes` {text}, needs `Authorization: <token>`, to `Notes.create`.
- `GET /notes`, `GET /search?q=`, need the token, to `Notes.list_for` and `Search.find`.
- `main(port)` starts a `ThreadingHTTPServer` on 127.0.0.1.

Public functions (app/auth.py, `Auth`): `register(username, password)`, `login(username, password)` returns a token or None, `user_for(token)` returns a username or None.

Depends on: app/notes.py and app/search.py (other branch), the standard library only. Nothing in the project depends on server.py; server.py depends on all three modules through module-level singletons `AUTH`, `NOTES`, `SEARCH`.

Data flow for a request:
1. `ThreadingHTTPServer` accepts the socket and starts one thread per connection (HTTP/1.0, no socket timeout, listen backlog 5).
2. `do_POST` reads `Content-Length` bytes and parses JSON. `do_GET` parses the query string.
3. `_user()` maps the raw `Authorization` header to a username through `AUTH.tokens`.
4. The route calls Auth, Notes or Search on the shared singletons, with no locks.
5. `_send` writes JSON. In `do_POST`, `ValueError` becomes 400 and any other exception becomes 500 with the full traceback in the body. `do_GET` has no error handling.

State: all in process memory. `Auth.users` (username to unsalted SHA-256 of the lowercased password), `Auth.tokens` (token to username, never removed), `Notes.notes`, `Search.cache`. Nothing is persisted; a restart loses everything.

Files read in full: README.md, app/auth.py, app/server.py, app/notes.py, app/search.py, tests/test_auth.py, tests/test_search.py.

## Findings

### A1. Passwords are not case-sensitive. High
- Where: app/auth.py, `Auth.register` and `Auth.login` (`password.lower()` on lines 15 and 19).
- What happens: register `victim` / `Tiger-77`, then `POST /login {"password": "tiger-77"}` returns 200 with a token. The README says "Passwords are case-sensitive."
- How it was found: test `test_passwords_are_case_sensitive` and `test_password_case_sensitive_over_api` fail; confused-user journey "login caps lock on" got 200; brute-force script "all-lowercase guess: 200".
- Suggested fix: hash the password as given, with no `.lower()`.

### A2. Password hashes are unsalted fast SHA-256. High
- Where: app/auth.py, `register`.
- What happens: the stored value is `sha256(lower(password))`. Two users with the same password have the same hash, and the hash is cheap to brute-force offline. Lowercasing also shrinks the search space.
- How it was found: code reading; the brute-force script printed the same hash prefix for any user with that password.
- Suggested fix: `hashlib.scrypt` or `pbkdf2_hmac` with a per-user random salt, compared with `hmac.compare_digest`.

### A3. Login tokens never expire and pile up without limit. High
- Where: app/auth.py, `login` (`self.tokens[token] = username`); no logout route in server.py.
- What happens: each login adds a token that is never removed. Long run, 8 clients logging in and listing notes for 240 s:

  | t (s) | journeys | RSS MB | traced MB | tokens |
  |---|---|---|---|---|
  | 1 | 7 | 63.5 | 13.48 | 12853 |
  | 64 | 11518 | 70.9 | 15.61 | 24360 |
  | 128 | 23173 | 78.4 | 17.23 | 36019 |
  | 193 | 34827 | 85.8 | 19.80 | 47671 |
  | end | 43006 | 100.2 | 20.91 | 55856 |

  Growth is linear and does not level off. The top tracemalloc lines are json/decoder.py:353 (8992 KiB, the username copies held as token values), secrets.py:59 (4418 KiB, 55856 tokens) and app/auth.py:22 (1877 KiB, the dict). About 170 bytes per login. Old tokens also stay valid after a new login ("old token after re-login: 200").
- How it was found: long run with tracemalloc and psutil.
- Suggested fix: give tokens an expiry and prune them, add `POST /logout`, and cap tokens per user.

### A4. Server error responses leak full tracebacks. High
- Where: app/server.py, `do_POST`, `except Exception: return self._send(500, {"error": traceback.format_exc()})`.
- What happens: `POST /login` with body `[]` returns 500 `{"error": "Traceback (most recent call last):\n  File \"<project path>/app/server.py\", line 39, in do_POST ..."}`. The same happens for register with an int, list or dict password or username, and for login with the password field missing. It exposes absolute paths and source lines.
- How it was found: hostile-user journey (6 inputs gave 500 with traceback); test `test_errors_do_not_leak_tracebacks` fails.
- Suggested fix: log the traceback on the server and return `{"error": "internal error"}`.

### A5. Concurrent note creation through the API loses notes. High
- Where: app/server.py calls the shared `NOTES.create` from many threads with no lock. The race itself is in app/notes.py (`next_id` read, `time.sleep(0.001)`, then write), which belongs to the notes branch.
- What happens: 10 users in parallel, 3 notes each: 30 notes acknowledged with 201, 16 unique ids, 8 of 10 users saw the wrong notes afterwards. 50 users: 87 acknowledged, 52 unique. Later notes overwrite earlier ones with the same id. The README says "Each note has a unique id."
- How it was found: crowd script; test `test_concurrent_note_creation_gives_unique_ids` fails.
- Suggested fix: a lock around id allocation in Notes, or `itertools.count`. Shared with the notes branch audit.

### A6. Bad input gives 500 instead of a clear 400. Medium
- Where: app/auth.py `register` and `login` (no type checks; `None.lower()` and `int.lower()`), app/server.py `do_POST` (`body.get` on non-object JSON).
- What happens: `POST /login {"username": "sam"}` with a registered user returns 500 (`AttributeError: 'NoneType' object has no attribute 'lower'`). Body `[1,2]`, `"text"` or `5` returns 500. `{"username": [1]}` returns 500 (unhashable list).
- How it was found: tests `test_register_non_string_password_is_a_value_error`, `test_login_with_missing_password_returns_none`, `test_login_missing_password_is_client_error_not_500`, `test_non_object_json_is_400` (3 cases) fail.
- Suggested fix: check `isinstance(body, dict)` and that username and password are non-empty strings, and raise `ValueError` otherwise.

### A7. GET errors drop the connection with no response. Medium
- Where: app/server.py, `do_GET`, which has no try/except.
- What happens: `POST /notes {"text": 123}` is accepted with 201. After that, every `GET /search?q=...` for that user closes the connection: client gets `RemoteDisconnected: Remote end closed connection without response`; the server log shows `AttributeError: 'int' object has no attribute 'lower'` from app/search.py:10. The user's search is broken until restart.
- How it was found: hostile-user journey and edge probe; test `test_get_errors_still_return_a_response` fails.
- Suggested fix: same error handling in `do_GET` as in `do_POST`; reject non-string `text` in `POST /notes`.

### A8. Server breaks at 25 to 50 concurrent clients. Medium
- Where: app/server.py, `main` uses `ThreadingHTTPServer` with the default `request_queue_size = 5`.
- What happens: throughput stays near 400 rps at every concurrency level. Errors start at 25 concurrent logins and grow from there:

  | endpoint | concurrency | rps | p50 | p95 | errors |
  |---|---|---|---|---|---|
  | GET /notes | 25 | 434 | 13.9 ms | 21.5 ms | 0 |
  | GET /notes | 50 | 430 | 14.1 ms | 1022 ms | 1 timeout |
  | GET /notes | 200 | 445 | 16.0 ms | 4951 ms | 60 timeouts |
  | POST /login | 25 | 304 | 17.5 ms | 79.3 ms | 2 resets |
  | POST /login | 50 | 387 | 16.3 ms | 1031 ms | 54 resets |
  | POST /login | 200 | 466 | 17.1 ms | 2270 ms | 342 resets |

  The 1 s p95 matches TCP SYN retransmits after the backlog of 5 fills. The client ran on the same machine in Python, so the rps ceiling is partly the client.
- How it was found: load ramp, 5 s per step.
- Suggested fix: raise `request_queue_size` (for example 128), and run behind a production server if real load is expected.

### A9. Slow or short request bodies hold a thread forever. Medium
- Where: app/server.py, `do_POST` reads `Content-Length` bytes with no socket timeout and no size limit.
- What happens: 50 clients that send `Content-Length: 100` and 2 bytes held 50 threads and 50 sockets (threads 1 to 51, fds 5 to 55) for as long as they stayed open. `Content-Length: -1` made the server read to EOF and send no reply within 3 s. There is no upper limit, so a 5 MB note and a 1 MB username were both accepted.
- How it was found: edge probe with raw sockets and the stats dump.
- Suggested fix: set `timeout` on the handler, reject negative or large `Content-Length` with 400 or 413.

### A10. No limit on login attempts. Low
- Where: app/server.py `/login`.
- What happens: 1000 wrong passwords in 2.95 s, all 401, then the right password still returns 200. No delay or lockout.
- How it was found: brute-force script.
- Suggested fix: per-user and per-IP attempt limits with backoff.

### A11. Error messages echo parser internals. Low
- Where: app/server.py `except ValueError as e: ... str(e)`.
- What happens: `Content-Length: abc` returns `{"error": "invalid literal for int() with base 10: 'abc'"}`; bad JSON returns the decoder message.
- How it was found: hostile-user journey.
- Suggested fix: fixed messages such as "invalid request body".

### A12. Usernames are not normalised or limited. Low
- Where: app/auth.py `register`.
- What happens: `<script>alert(1)</script>...`, `' OR 1=1 --...`, `../../etc/passwd...` and a 1,000,000 character name all register with 201. No current route renders or uses them as paths, so there is no exploit here today, but any future UI or file use would need to escape them.
- How it was found: hostile-user journey.
- Suggested fix: a length limit and an allowed character set.

Seen in passing, owned by the notes and search branches: `Notes.create(tags=[])` uses a shared mutable default, so every note of every user shares one growing `tags` list (`["note", "note", "note", "note"]` after 4 notes); and `Search.cache` is never invalidated or bounded.
